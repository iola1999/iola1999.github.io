这次给 Codex 派了个硬活：把一只随手抓来的 USB 上网卡改造成无头短信收发站。主力模型用的是 GPT 6.1 Sol。

需求很简单，几张偶尔用来收验证码的卡总得有个去处，扔在手机里费电还得维护，不如搞个设备插在 Linux 主机上挂着。之前看人拿大疆 4G 模块改过类似的东西，手头正好有些闲置硬件，干脆自己动手。

本来只想问问可行性，结果聊着聊着尺度就失控了：能不能把原固件完整倒出来？能不能自己写个小程序塞进去？能不能直接编译刷机？

折腾到现在，固件通过 USB 备份出来了，自己写的 C 程序也成功跑在设备上。先做了 Mac 应用，跑通短信收发和双向通话，后来又做了网页版本，把模块接到 NAS 上。先把这段过程记下来。

## 先翻出来的是一台红米 1S

最早看中的其实是抽屉里的红米 1S。这老机子早就 root 过，网上开源内核和第三方系统一抓一大把，本来打算刷个轻量 Linux 进去直接管 SIM 卡。

Codex 当时帮我把整个方案拆了一遍：Linux 内核要改哪些驱动、基带跟系统怎么通信、抛弃安卓后哪些服务必须保留，还查了远程双向通话音频如何采集和送回。

可现实马上泼了冷水——这破手机要用的 2G 网络，本地早退网了。基带连不上网，折腾系统也是白搭，只能换方案。

翻箱倒柜，总算翻出了以前买的一只 USB 上网卡。

## 我拆外壳，它查芯片

这东西本来就是插电脑上靠网页后台配流量、发 Wi-Fi 的。撬开外壳，里面倒是有个标准的 SIM 卡槽，但插上自己的卡后，根本不按预想的逻辑工作。

我把 PCB 正反面的芯片丝印拍给 Codex，让它顺藤摸瓜。板子型号 CSM45L，核心是展锐 US8310AM。核对完资料凉了一半：这货跑的是厂商的定制 RTOS，网上那些把同类上网卡刷成 OpenWrt 的骚操作完全照搬不了。

调试时还发现个诡异现象：开机后反复轮询 SIM 卡状态，刚通电时能抓到卡，过一会儿状态就变了。单次查询根本看不出猫腻，必须写个循环连续打日志才抓到这个时序坑。至于底层到底是哪段代码在搞鬼，只能进固件里慢慢扒。

## 没 SDK？那就硬着头皮找替代品

最偷懒的法子是通过 USB 端口发 AT 指令，直接调原固件收发短信。不过我更想把控制权抓在手里，写个精简的设备端程序，直接把短信通道暴露出给主机，把原厂那套臃肿的业务逻辑替换掉。

底层蜂窝协议栈和基带驱动当然得留着，LTE 鉴权和拨号这块水太深，没必要自己去碰。我的目标很窄：搞定 SIM 卡管理、读写短信，以及和主机的通信。

麻烦在于，展锐这块芯片根本没有公开的 SDK。Codex 一直把“缺乏厂商头文件和工程源码”标为后续的大红灯。好在我没打算放弃，让它继续满世界刮地皮。

后来居然真被它翻出来一个 D-Link 同平台的官方固件包。里面除了刷机包，竟然带了符号信息和调试产物。我们直接丢给 IDA 和分析脚本，对照着手上这块板子的二进制一点点啃。

虽说没有完整的工程源码，但有了这些带函数名的参考样本，大批原本死寂的内存地址总算有了名字，函数签名和消息结构也有了线索。

## 刷机前，先把退路留好

谁也不想为了备份去热风枪吹 Flash 上编程器，必须想办法从 USB 把全盘倒出来。

Codex 找出了固件里留存的诊断读取接口，先读出一部分内存代码进行交叉比对。接着，它基于开源的底层加载器改了一个 NAND 读取工具，把控制器能访问的原始 NAND 数据完整读出来，并处理硬件 ECC 校验。

在参考固件里翻到原厂加载器时，我差点直接拿来用。好在 Codex 多看了一眼反汇编，发现这东西在等主机指令前，会触发自动格式化或重写配置分区。

加载器上电后会执行哪些操作，必须先查清楚。最后我们用了自己写的小程序，严格限定读写范围，完成全盘备份。

备份做完，回写测试也必不可少：划定应用区、擦除、写回、再读出来对比、最后重启。确认原厂固件还能正常活过来，才敢进行下一步的魔改。

## 头版固件：让它活着回个名字

试水的第一版极其克制，只写了个极小的 C 程序：上电后接管指定位置，通过 USB 回传一个自定义的版本字符串。

没有 SDK 的后果就是硬编码地址：保留原厂的底层和驱动，把编译好的二进制硬塞进分析好的空闲函数区，重新算校验和打包。

第一次刷完满怀期待地重启——好家伙，USB 直接没响应了，拔插好几次毫无反应。得，变砖了。好在 PCB 上留了复位短接点，按住按键重新上电，Codex 迅速在终端守株待兔，用下载模式把原厂固件捞了回来。

失败原因没法在纸面上完全理清，调整了内存重定位和启动标记后，第二版总算过了。插上电脑，终端甩回来一行字：

```text
sim-pool app/0.1

```

把内存读出来核对无误，再刷回原厂固件确认硬件没废。到这里，编译、刷入、执行这条闭环算是跑通了。

## 终于把短信抠出来了

到了最核心的短信环节，不出意外又卡了一道。

Codex 找到了平台层处理短信的回调函数，写好了注册逻辑。结果满怀期待地发了条测试短信，终端死活没反应。排查了半天才发现，回调拿到的只是底层裸事件，部分关键消息头要在后续的分发流程里才会被填充。我们拦截得太早，把消息当垃圾过滤掉了。

修正逻辑后，自研的固件终于通过 USB 往外吐出了两条真实的短信内容。Mac 上跑个脚本一解：一条是测试用的英文，一条是中文短信，反复读很多次，数据非常稳定。

读出旧短信后，继续把 SIM 和短信初始化补上，LTE 注册也正常了。接着从 Mac 通过自己的 USB 接口发了一条测试短信，手机确实收到了；用手机回一条，设备也读到了，发送人、时间和正文都能解析。到这里，短信的一发一回算是跑通了。

原厂那些臃肿的业务逻辑还没全清掉，目前只是接管了一部分初始化和 USB 交互。离做成一个真正稳定托管的设备还有段距离。

## 从脚本到 Mac 应用

短信能收发后，每次还在终端里敲命令也不太方便，于是接着做了个 SwiftUI 的 Mac 应用，叫 SIM Pool。应用直接通过 USB 操作模块，左侧切换电话和短信，查看会话、搜索和回复都在窗口里完成，运行时不用另开 Python 服务。

短信存进本机 SQLite 数据库，断开设备也能查看。收到的短信先归档并读回核对，再从模块里清理，免得设备存储被验证码塞满。运营商发回来的中文短信也试过了，两段长短信能在应用里拼成一条。

## 电话也接进来了

接着又想试试：既然模块本身支持语音，能不能直接拿 Mac 的麦克风和扬声器打电话？

这部分继续用平台原有的 IMS 通话协议栈。没有为通话再刷一版固件，Mac 在连接时把一小段 C 扩展加载进模块 RAM，调用原有的网络和通话函数。语音帧通过 USB 在模块和电脑之间传输，Mac 端用 AMR 编解码库处理，并通过系统音频接口采集和播放。

先从 Mac 拨出去，手机能收到也能接听，但听到的全是噪音，应用还报 Core Audio 错误。查日志发现，Mac 端采集和播放的音频格式对不上，先把这部分修掉，再继续查来电。

来电更折腾：另一部手机拨进来，应用没有反应，对方最后被转到了运营商智能助理。一开始连来电请求都看不到，后来抓到网络包，才发现 IMS 消息被拆成了 IPv6 分片，扩展漏掉了接收重组后的解密处理。接收修好后能看到来电请求了，模块却又返回 `580 Precondition Failure`。继续查，发现较大的 SIP 回复在发送前也被分片了，这些分片跳过了加密。

最后复用平台已有的分片重组和发送函数，把上下行处理补齐。再用另一部手机拨入，这次应用终于弹出来电，接听后手机和 Mac 两边说话都正常，之前的噪音和异常挂断也没再出现。

外拨后来又遇到接听瞬间断线。查到最后，模块重复触发读取通知，第二次读取返回 `EWOULDBLOCK`，原有 SIP 代码就把 TCP 连接关了。调整通知时序，再修正跨缓冲区的解密数据处理后，外拨接听和双向语音也通过了实测。

## 把模块接到 NAS 上

先做的 Mac 应用已经能收发短信、接打电话。后来用下来，还是觉得网页更灵活，换台电脑或用手机也能访问。于是又做了网页版本，把 USB 模块插到 NAS 上，也就不用占着 Mac 的 USB 端口了。服务用 Docker 常驻运行，源码在 NAS 本地构建。

Python 服务独占 USB，负责设备连接、短信归档和通话控制，短信存在 NAS 的 SQLite 数据库里。浏览器通过 WebRTC 使用当前电脑或手机的麦克风和扬声器，NAS 本身不用接音频设备。网页通话需要 HTTPS，服务外面加了一层反向代理。

迁移时最费时间的还是声音。固定音调测试明明通过了，实际通话却有强噪音，最后查到旧版 AMR-WB 解码库处理静音帧有问题，换到 0.1.6 后才恢复正常。另一次断续则跟模块的静音检测有关：它减少了发包，主机排队的音频却还在持续增加。主机接管音频时关闭这项检测、退出时恢复，来电连续通话和外拨复测才都正常。

## 电脑网页和手机 H5

界面统一用了 Material Design，主导航只留电话、短信和设置。桌面上分栏查看会话和正文，设备状态与诊断放进设置；手机 H5 则用底部导航，点进会话后看全屏详情。刷新后能回到之前打开的内容，短信草稿和滚动位置也保留着。

收到短信和来电后，服务可以发 Bark、Web Push 或 Webhook 通知，点击通知能定位到对应内容。iPhone 上可以把页面加到主屏幕，打开后没有浏览器地址栏；Web Push 在页面关闭后也能收到。通知失败会按间隔重试，短信在别的设备上读过之后，还没发出的提醒会取消。

通话录音和超时自动接听也做完了。录音在音频就绪后开始，通话详情里可以播放、下载和删除。自动接听默认等 30 秒，然后播放提前合成好的问候语和滴声，邀请对方留言；留言有默认时长上限，也可以改问候语和音色。

## 后来补上的几个功能

短信这块加了一个本地分类模型。模型是从一个 iOS 短信过滤应用里提取的，权重和词表直接打包进服务，分类在 NAS 上完成，不把短信发给外部接口。它先把短信分成正常、垃圾和交易三类，交易短信再细分金融、运营商、天气、订单物流等。垃圾短信仍然保存并显示在会话里，只是不生成提醒；已有短信在服务启动后补一遍分类结果。

来电识别也接上了。呼入号码和短信发送号码会查询公开的号码信息接口，显示骚扰或诈骗标记、公司名，以及普通号码的归属地和运营商。结果会出现在通话页、顶部来电提示、历史记录、短信会话和通知里。查过的号码按类型缓存一段时间，历史通话和短信在服务启动后补识别。通知最多等 1.5 秒，超时就先按号码发送，通话本身不受影响。

识别到骚扰号码后，可以选转到留言或直接挂断，默认转到留言。转到留言需要先开启留言信箱，没开启时会直接挂断。只有号码标记明确命中骚扰、诈骗、推销、中介、贷款、催收等短语时才会处理，公司名里带类似字样不会触发。号码标记本身可能误判，所以处理方式留给了用户。

通话状态也补全了：拨号、对方振铃、接通、保持和结束原因会显示中文，外呼的 SIP 响应和 Q.850 网络原因会翻译成常见含义。音频可以在 WebRTC 和 WebSocket 之间切换；浏览器音频断了，通话不会跟着挂断，换一台设备可以接管音频。登录连续失败三次会锁定七天，并给已配置的通知渠道发提醒。

## 功能清单

NAS 网页版目前有这些功能：

**电话**

- 呼入、呼出、接听、拒接和挂断，显示拨号、振铃、接通、保持等阶段
- 通话录音，详情页播放、下载和删除
- 超时自动接听和留言信箱，可改问候语、音色、等待时间和留言上限
- 来电识别：骚扰标记、公司名、归属地、运营商；骚扰来电可转到留言或直接挂断
- 呼叫失败时显示 SIP 响应和网络原因的中文说明
- WebRTC / WebSocket 两种音频传输；音频断开后保留通话，可换设备接管
- 通话历史和 JSON 导出

**短信**

- 收发、长短信拼接、会话列表、搜索和导出
- 垃圾短信和交易短信本地分类，垃圾短信不推送提醒
- 发送人识别，显示标记、公司名和归属地
- 已读状态同步，已读短信取消未发出的提醒
- 自动清理模块和 SIM 卡里的已接收短信，默认关闭

**通知**

- Bark、Web Push 和 Webhook，可同时配置多个目标
- 来电、短信、登录失败提醒，失败重试和发送记录
- 点击通知打开对应通话或短信

**设备与页面**

- 通话、短信和设置三个栏目，桌面分栏、手机底部导航
- 页面可添加到主屏幕，支持深色主题和横屏
- 刷新后保留所在栏目、滚动位置和短信草稿
- 设备诊断、USB 拔插恢复和手动重连
- 登录保护、更新提醒和页面缓存清理

## 这次折腾的几点体会

这次 Codex（配合 GPT 6.1 Sol）帮忙最多的，是把查芯片、对照同平台符号、写 USB 工具这些工作连续做了下来。没有公开 SDK，很多接口只能从固件里确认，结果还得拿到设备上试。

整个过程最管用的还是一次只验证一件事：先确认能不能读、写坏后能不能恢复，再输出版本号、调短信接口。到了通话，能接通之后还有音质和连续性要查。固定音调能正常播放，遇上真实通话的静音帧照样会出问题，这次算是记住了。
