## 前言

最近给 Codex（主力模型使用 GPT 6.1 Sol）安排了一个挺折腾的硬件改造任务，目标是把手头一个闲置的 USB 4G 随身 Wi-Fi 上网卡，改造成能长期插在 Linux 主机或 NAS 上做短信转发和接打电话的独立通讯模块。

起意做这件事是因为手头有几张平时只用来收验证码的副卡，一直塞在备用手机里不仅费电，隔三差五还得惦记着充电维护，不如直接做个低功耗的 USB 设备插在常年开机的服务器上托管。之前在网上看到有人拿大疆的 4G 模块改过类似的东西，正好抽屉里翻出了几件吃灰的旧硬件，就干脆自己动手试一试。原本我只是想跟 AI 聊聊这件事在技术上通不通，结果顺着话头越聊越深，从怎么通过 USB 把原厂固件完整读出来，一路聊到了怎么往原厂固件里塞自定义 C 程序、怎么直接编译刷机。

折腾到现在，整套链路已经全部跑通了。我们不仅通过 USB 完成了全盘固件备份、让自写的 C 代码在板子上顺利跑了起来，还先做了一版支持短信收发与双向语音通话的 Mac 原生应用，随后又把模块迁到 NAS 上做成了一套完整的 Web 与手机 H5 系统，把通话录音和自动接听留言信箱、来电识别与本地垃圾短信分类全接了进来。下面按时间顺序把这段改造过程记一下。

## 硬件选型、拆机与全盘固件备份

### 从红米 1S 转向展锐 US8310AM 上网卡

最开始我从抽屉里翻出来的其实是一台早年 root 过的红米 1S。因为这台旧手机在网上能找到不少现成的开源内核和第三方 ROM，我最初盘算着直接给它刷一个裁掉图形界面的轻量级 Linux 进去，专门用来管 SIM 卡。Codex 当时帮我把整套方案拆得很细，包括 Linux 内核需要改哪些驱动和基带处理器怎么跟主系统通信，以及砍掉 Android 框架后必须保留哪些守护服务，甚至连怎么远程采集和回传双向通话音频都查好了。结果刚准备动手就发现这台老机器只支持当时的 2G 语音与短信网络，而我这边的 2G 基站早就退网了。基带连信号都注册不上，系统改得再好也没用，只能换硬件。

重新在杂物箱里翻了一圈，总算找到了一个以前买的 USB 随身 Wi-Fi 上网卡。这东西原本的用法是插在电脑上提供无线热点，自带一个简陋的网页后台用来配流量。撬开塑料外壳后，可以看到主板上留着一个标准的物理 SIM 卡槽，但直接插上自己的手机卡上电后，原厂系统的行为跟我们预想的完全不一样。

我把 PCB 正反面的芯片丝印微距拍下来发给 Codex 去查资料，确认板子型号是 `CSM45L`，主控芯片用的是紫光展锐的 `US8310AM`。核对完芯片规格后多少有点失望，因为这颗芯片跑的是厂商高度定制的实时操作系统（ThreadX / MOCOR），网上流传的那些把高通方案随身 Wi-Fi 直接刷成 Debian 或 OpenWrt 的现成教程在这块板子上完全用不上。而且在初期串口与 USB 调试时还碰到了一个很怪的时序问题，开机后如果只做单次查询看不出异常，写个循环连续轮询打日志才发现，刚上电那几秒明明能正常读到物理 SIM 卡，过一小会儿卡状态就会莫名其妙地切走。要想搞清楚底层到底是哪段原厂代码在切卡，就只能把固件扒下来做逆向分析了。

### 寻找同平台参考固件与全盘 NAND 备份

其实如果只是想收发短信，最省事的路子是直接顺着现有的 USB 虚拟串口发标准 AT 指令。但我更希望能彻底接管控制权，自己在板子上跑一段精简的设备端程序，把干净的短信和语音通道直接暴露给宿主机，同时把原厂固件里那些跟切卡、云控相关的冗余逻辑替掉。当然，底层的 LTE 蜂窝协议栈、基带驱动和网络鉴权过于庞大复杂，这部分肯定得原样保留，我们只需要接管上层的 SIM 卡管理、短信读写以及 USB 主机通信即可。

真正的阻碍在于展锐这颗 `US8310AM` 在公开渠道根本找不到完整的官方 SDK。Codex 在前期的评估里一直把「缺少厂商头文件与工程源码」列为最大的推进风险。好在我们没有直接放弃，我让它顺着芯片代号 `UIS8310` 和 `UMS9117` 继续在全网搜寻同平台资料，最后还真让它找着了一份 D-Link 同平台设备（`DWR-930M`）流出的官方固件包。这份包里不仅有刷机镜像，居然还完整保留了编译生成的 `.axf` 调试产物与 `.map` 符号表。我们立刻把这份参考固件丢进 IDA Pro，配合自写的辅助脚本对照手头这块板子的二进制镜像逐段比对，原本密密麻麻全是裸地址的固件一下子多出了大批准确的函数名、参数签名与内部消息结构。

在真正动手改固件之前，有一条底线必须先守住，那就是不开风枪拆焊 Flash 芯片的前提下，必须先通过 USB 把板子上的全盘原始固件完完整整地备份出来，并且验证好写坏之后的救砖恢复流程。Codex 先从原厂固件里翻出了残留的诊断读取接口，读出一小部分内存代码做交叉核对；随后又基于开源的展锐底层引导协议，改写出了一套专门的 NAND 读取加载器（FDL），在板子进入下载模式后直接把 Flash 控制器能访问到的原始 NAND 页连带硬件 ECC 校验数据完整导出到了电脑上。

这里还避开了一处很险的隐患。我们在参考固件包里其实找到过一份现成的原厂加载器，当时差点就直接拿它往板子里发了，好在 Codex 提前把那份二进制反汇编检查了一遍，发现原厂加载器在启动初始化、还没开始接收宿主机指令之前，就会擅自触发自动格式化或者覆写关键配置分区。看清这个逻辑后，我们果断弃用了原厂加载器，全程改用自己编写并严格锁死读写地址范围的微型加载器完成了全盘备份。拿到备份文件后，我们又专门在 Flash 的应用区划出一块空间，实地跑了一遍「擦除与写回、回读比对以及重启进原厂系统」的完整往返测试，确认随时都能无损救砖，这才放心开始改代码。

## 植入自定义 C 代码与打通短信收发

### 第一版自定义固件与下载模式救砖

为了控制单步变量，我们写的第一版自定义代码功能极度精简，只有一个几十行的微型 C 程序，目标是板子上电启动后接管指定入口，通过 USB 向电脑返回一个自定义的版本号字符串。因为没有官方 SDK 和链接脚本，所有的外部函数调用都得直接填前面从符号表里抠出来的绝对地址；编译生成机器码之后，在不破坏原厂底层协议栈与驱动的前提下，把新代码塞进事先找好的固件空闲区，重新计算头部校验和并打包成刷机镜像。

第一次刷入新固件后，我满怀期待地给板子断电重插，结果电脑上的 USB 列表毫无反应，反复拔插几次也是彻底死机，第一版不出意外地刷砖了。好在拆机时就已经确认过主板上留着进下载模式的复位短接点（`KEY` 测试点），我拿镊子按住短接点重新插上 USB，等在终端前面的 Codex 立刻捕获到了 `1782:4d00` 下载模式握手信号，几秒钟就把原厂固件原样刷了回去。

靠静态看代码很难一眼定位挂死的具体指令，我们随后调整了内存重定位方式与启动跳转标记，重新打包刷入第二版。这次重新插上电脑后，终端里终于稳稳地打出了一行自定义输出。

```text
sim-pool app/0.1
```

把运行时的内存段重新读回电脑比对确认分毫不差，再刷回原厂备份确认硬件没有任何损伤，从交叉编译与二进制打补丁，到刷入 Flash 和真机上电执行这整条自定义代码链路就已经彻底打通了。

### 找准事件分发时机读出真实短信

跑通自定义代码后，马上进入最核心的短信收发环节。Codex 顺着参考符号表找到了平台层负责处理短信的回调函数，写好了自己的注册与拦截逻辑刷进去，结果我拿手机往板子里的卡发了一条测试短信，终端里却静悄悄的没有任何输出。

顺着调用链前前后后查了很久才搞明白，我们最开始挂钩的那个回调函数拿到的其实只是最底层的裸事件，此时短信结构里的好几个关键消息头字段根本还没来得及填充，要等到后续的分发流程走完才会被写进去。因为我们拦截的位置太靠前，自定义的检查逻辑看到头部字段全是空的，直接把刚收到的真短信当成无效垃圾包给过滤掉了。

把挂载点往后挪到完整的消息分发阶段后，自研固件终于通过 USB 接口吐出了卡里存着的两条真实短信数据。在 Mac 上跑起解析脚本一看，一条是测试用的英文短信，另一条是中文短信，反复循环读取几十次数据都非常稳定。读出存量短信之后，我们顺势补齐了设备端的 SIM 卡与短信子系统初始化流程，确认 LTE 网络注册正常，接着直接从 Mac 终端通过自己的 USB 通道发了一条测试短信出去，几秒钟后旁边的手机顺利收到；再拿手机回发一条，板子也实时捕获并解析出了完整的发件人号码、时间戳和正文。到这一步，不依赖原厂网页后台的纯自定义 USB 短信收发就正式跑通了。

## 开发 Mac 桌面应用与接入 IMS 双向通话

### 用 SwiftUI 封装 SIM Pool 桌面端

虽然在命令行里跑脚本已经能收发短信了，但日常每次看验证码还得打开终端敲命令终究不够直观。于是我们用 SwiftUI 做了一个原生的 macOS 桌面应用，起名叫 `SIM Pool`。这个应用在进程内直接通过 USB 接口跟上网卡模块通信，不需要在后台另外挂 Python 服务；界面左侧可以在电话和短信之间切换，右侧直接看会话列表、做关键字搜索和直接回复。

为了防止上网卡模块里那点有限的存储空间被日积月累的验证码塞满，应用在每次收到新短信后，会先写入 Mac 本机的 SQLite 数据库归档，再从数据库读回来做一次完整性核对，确认无误后自动把模块里的原始记录删掉，这样平时哪怕断开 USB 设备也能随时在应用里翻看历史短信。针对运营商经常下发的超长中文短信，应用层也补好了多段分片自动拼接逻辑。

### 在 RAM 中加载通话扩展并解决 IPv6 分片加密

短信功能稳定下来之后，我又动了新的念头。既然这颗展锐基带本身就带着完整的语音通话能力，能不能干脆连电话功能也一起接管过来，直接用 Mac 电脑的麦克风和扬声器接打电话？

为了不频繁擦写 Flash，这次做语音通话我们没有重新刷写底层的固件分区，而是改成了「动态加载 RAM 扩展」的方案。底层的 VoLTE / IMS 语音协议栈依然直接复用原厂固件里现成的实现；每次 Mac 应用连上 USB 模块时，会动态把一小段编译好的 C 语言通话扩展直接注入到模块的空闲 RAM 里运行，由这段扩展去调用原厂的网络与通话控制函数，并把实时的语音帧通过 USB 批量传输通道在模块与电脑之间双向搬运。Mac 客户端拿到语音帧后调用 AMR 编解码库还原成 PCM 音频，再交给系统的 Core Audio 接口播放和采集。

先测从 Mac 主动往外拨号。电话顺利拨通了，手边的测试手机也能正常振铃并接听，但耳机里听到的全是一片刺耳的噪音，控制台里还在不停刷 Core Audio 的状态报错。核对日志发现是 Mac 端采集和播放两侧配置的音频采样格式不一致，先把本地音频管线对齐修复后，外拨的声音就清楚了。

真正的硬仗在接听来电上。拿另一部手机往上网卡的号码拨过去，Mac 应用上一点反应都没有，电话响了几声后直接被转进了运营商的语音信箱。最开始我们在模块侧甚至连收到的来电请求都看不到，直到在底层抓了网络包才查出原因。原来运营商下发的 IMS `INVITE` 来电信令因为报文较长，在网络层被拆成了多个 IPv6 分片下发，而我们的扩展代码在接收路径上漏掉了分片重组之后的 IPsec 解密步骤，导致整条来电请求直接被丢弃。把接收端的重组解密补上之后，应用终于能看到来电请求了，可一点接听模块却又往回吐了一条 `580 Precondition Failure` 报错。顺着发送路径继续往下查，发现模块往外回复的较大体积 SIP 应答报文同样触发了 IPv6 分片，而这批拆出来的分片在发往基带前竟然跳过了加密流程。

最终我们直接找出了原厂平台里现成的分片重组与加密发送函数，把上下行两条路径全部换用原厂内部接口接好。再拿手机拨入测试，Mac 应用当场弹出了来电提醒，点击接听后电脑与手机两侧的双向语音清晰稳定。后来在反复测试外拨时还逮到了一个「接听瞬间立即断线」的偶发问题，排查发现是模块底层重复触发了两次 socket 读取通知，第二次读取拿到 `EWOULDBLOCK` 状态码后，原有的 SIP 处理逻辑误以为连接异常直接把 TCP 套接字关掉了。调整完通知触发时序并修好跨缓冲区的解密数据拼接后，外拨与来电的长时间双向通话就全都稳住了。

## 迁移到 NAS 网页端与补齐日常通讯功能

### 接入 NAS 容器与解决静音帧噪音

Mac 桌面版用了一段日子后，我还是觉得绑定在单台电脑上不够自由，如果能做成网页版，把 USB 上网卡直接插在家里 24 小时开机的 NAS 上，平时无论坐在哪台电脑前还是出门在外掏出手机都能随时访问，而且还能把 Mac 宝贵的 USB 口腾出来。于是我们又动手做了一套 Web 与手机 H5 版本，在 NAS 本地直接从源码构建 Docker 镜像常驻运行。

在新的容器架构下，后端的 Python 服务独占管理 USB 设备，统一负责设备断线重连、短信 SQLite 落盘归档以及通话状态机控制；前端浏览器则通过 WebRTC（同时支持切换为 WebSocket 音频流）直接调用当前电脑或手机自带的麦克风与扬声器，NAS 主机本身完全不需要插任何声卡或音频外设。为了满足移动端浏览器在非本地环境下调用麦克风的安全限制，服务外层还配了一层 HTTPS 反向代理。另外我们还把音频通道与底层通话状态做了解耦，万一通话中途浏览器页面不小心关了或者网络闪断导致音频流断开，模块上的真实通话并不会因此挂断，随时掏出另一台设备打开网页就能无缝把音频重新接管过来。

把音频链路从 Mac 原生应用迁到 Web 服务的过程中，最费工夫的依然是声音质量排查。当时用固定频率的测试音调跑环回测试明明一切正常，可一接通真实的手机通话，耳机里就会冒出很强的底噪。前前后后排查了一圈，最后定位到是服务端起初集成的旧版 `AMR-WB` 解码库在处理真实通话里的舒适噪音与静音帧（SID frame）时存在缺陷，把解码库升级到 `0.1.6` 版本后噪音当场消失。紧接着又处理了一次通话几分钟后声音开始断断续续的问题，查下来跟模块底层的静音检测（VAD）机制有关，对方不说话时模块自动减少了上行发包频率，但宿主机这边的音频抖动缓冲队列却还在按固定节奏累加延迟。后来改成了在宿主机接管通话音频期间临时关掉模块的静音检测、挂断退出时再自动恢复，无论是来电长谈还是外拨复测就都彻底顺畅了。

### 桌面网页、手机 H5 与多通道消息推送

前端界面统一按 Material Design 风格做了响应式设计，顶层导航只保留「电话」「短信」和「设置」三个核心栏目，支持深色主题与横屏布局。在电脑桌面浏览器上采用左右分栏布局，左边看会话列表、右边看短信正文或通话详情，设备状态监控与 USB 拔插自动恢复、手动重连以及登录保护和缓存清理都收进了设置页；到了手机浏览器上则自动切换为底部导航栏，点开会话后进入全屏详情页。前端还做了完整的状态保持，平时不小心刷新页面也能直接回到刚才停留在的栏目、恢复滚动位置并保留还没发出去的短信草稿。下面三组拼图展示了桌面端与手机端的八个实际页面（图中的电话号码与短信内容、通话记录与配置项均使用模拟数据生成）。

在此基础上，我们还把通话双向录音和超时自动接听留言信箱做了进来。通话录音在双方音频通道就绪后自动开始录制，结束后可以直接在通话详情页里在线回放、下载音频文件或删除记录，全部通话历史与短信会话也支持一键导出为 JSON。自动接听留言信箱默认在振铃满 30 秒无人接听时触发，系统会自动接起电话，向对方播放一段提前合成好的语音问候语和「滴」声提示音，引导对方留下语音留言；问候语文本与合成音色、振铃等待时长以及单条留言的最大时长上限都可以在设置页里随时调整。

### 本地垃圾短信分类、来电识别与留言信箱

日常挂着副卡用了一阵子后，每天涌进来的营销推广短信和骚扰电话成了新的烦心事，于是我又让 Codex 接着补齐了本地短信分类与来电号码识别两项功能。

短信分类直接集成了一个从某款 iOS 短信过滤应用里提取出来的轻量级本地模型，把模型权重和词表直接打包进 NAS 容器内部，所有文本分类推理全部在本地完成，绝不把任何一条私人短信发往外部第三方接口。模型会先把收到的短信分为「正常」「垃圾」和「交易」三大类，其中交易类短信还会进一步细分为金融与运营商、天气以及订单物流等子标签。被判定为垃圾营销的短信依然会正常入库并显示在会话列表里供随时备查，但系统会自动静默，不再触发手机推送打扰；服务初次启动时也会自动把数据库里的历史存量短信全部补跑一遍分类。

来电与短信发送方号码识别则是通过查询公开的号码信息接口实现的，用来显示骚扰或诈骗标记、企业名称，以及普通号码的归属地与所属运营商。识别出来的信息会同步展示在实时来电弹窗与通话详情页、历史记录列表与短信会话头以及推送通知里。查询过的号码结果会按类型在本地缓存一段时间，为了防止外部网络查询卡住实时通知，单次识别最多只等 1.5 秒，一旦超时就先按原始号码立即发出提醒，底层的通话接听本身更是完全不受查询耗时的影响。在呼叫状态展示上，前端不仅会把拨号与对方振铃、接通与保持以及挂断原因直接显示为中文，遇到外呼失败时还会把底层的 SIP 响应码与 Q.850 网络原因码自动翻译成通俗的中文说明。

有了号码识别结果后，针对标记为骚扰的来电就可以直接交由系统自动处理了。我们在设置里提供了「自动转入语音留言」和「直接挂断」两种处置方式（默认转为留言，若未开启留言信箱则回退为直接挂断）。考虑到公开号码库偶尔存在误标，为了避免误伤正常的快递或外卖电话，过滤逻辑设定了严格的触发条件，只有号码标记文本明确命中骚扰与诈骗、推销与中介或者贷款与催收这几类短语时才会自动拦截，单纯在企业名称里带有相关字样的号码并不会触发拦截，而且最终的处理策略完全交由用户在设置页自主开关。下面两组使用模拟数据生成的拼图展示了桌面端与手机端的来电识别和短信分类效果。

## 尾声与板卡硬件参数归档

回顾这次从拆机备份固件一路做到 NAS 网页通讯系统的全过程（界面联调阶段也直接复用了之前写的 [Codex Control Chrome MCP](/2026/06/26/Codex-Control-Chrome-MCP/) 让 Agent 自己在浏览器里验证页面交互），Codex（配合 GPT 6.1 Sol）帮我省下最多精力的地方，是把查芯片丝印与对照同平台符号表反汇编、写底层 USB 通信工具以及排查音频编解码问题这些跨度极大的工作连续不断地串了下来。在完全没有官方公开 SDK 的前提下，很多底层结构体的真实语义只能靠在反汇编里一点点抠，抠完还得立刻写探针刷上真机去试。
