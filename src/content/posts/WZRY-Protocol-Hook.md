## 前言

这次折腾的起因很简单。有天打开游戏停在登录选服界面，看着列表里排着的一千多个大区，我突然好奇这些区服名字到底是每次启动时从服务端实时拉取的，还是早就缓存在本地包里的，顺便想试试能不能动手改掉其中一个名字。本以为抓个包两三个小时就能看明白，结果顺着区服流量一路往下追，最后演变成了在游戏进程内拦截协议收发、从运行时内存导出完整 IL2CPP 符号表，并在电脑上搭了一套网页工作台来做实时字段改写与本地消息注入。

先交代一下测试环境。设备是一台已经获取 root 权限的真机，系统为 HyperOS 3（Android 16 / arm64），装有 KernelSU 和 Zygisk Next；测试的客户端版本是国服 `11.4.1.1`，内部原生库构建日期为 `2026-06-14`。后文提到的所有函数偏移都是绑定在这个特定版本上的 RVA，客户端一旦升级就需要重新定位，具体数值我都留在项目仓库的文档里了。

在按时间线展开排查过程之前，先放两个已经在实机屏幕上验证过的改写效果。目前游戏进程里常驻了一个自写的 Zygisk 原生模块，分别挂在协议的收包和发包入口上，每条经过的消息都会通过 IL2CPP 反射转成 JSON 发往主机端的工作台，在网页里配好规则就能按字段路径实时改写内容。第一个例子是把选服列表里的「手Q1区」单独改名，其余大区保持原样。

![选择服务器界面，手Q1区的名字被替换](/upload/images/2026-07-26-WZRY-Protocol-Hook/zone-renamed.png)

第二个例子是改写大厅左上角显示的玩家昵称。游戏自带的改名输入框最多只允许填 6 个汉字，而下面这张截图里直接显示出了 8 个汉字，超出控件宽度的后半截还被界面直接截断了。

![大厅左上角昵称显示为「任意长度改写验证」，后半截被控件宽度截断](/upload/images/2026-07-26-WZRY-Protocol-Hook/nickname-long.png)

实现这个效果只需要在工作台里配一行规则，把登录响应 `SCID_CMD_GAMELOGINRSP`（消息号 `1003`）里的 `szName` 字段替换掉。实际写入的是 26 个汉字（共 78 字节），而协议层的 TDR schema 给这个字段定义的定长上限其实是 64 字节。

```text
I WzryZg: [route] r msgid=1003 szName : System.Byte[] OK -> 新 Byte[78](任意长)
```

之所以客户端改名界面的 6 字上限和协议定义的 64 字节定长都没拦住这次修改，是因为我们的拦截点直接选在了协议反序列化（`unpack`）完成之后、业务代码读取之前的托管对象上。下面从最开始的抓包讲起，聊聊是怎么一步步走到这里的。

## 从网络层抓包转向进程内 Hook

### 解析明文区服表与放弃网络层改写

最开始用 `tcpdump` 抓包非常顺利，选服阶段拉取区服列表的流量完全是明文传输，区服名称和对应的 `LogicWorldID` 直接暴露在响应报文里。帧结构也很直观，以 `55 00 00 00` 开头，后面跟一个字节的字符串长度，再紧接着 UTF-8 编码的区服名。

顺着这份明文抓包，我把整张区服表完整解析了出来，一共 1,075 条记录，每条都由 `<平台><编号>区<诗意名>` 加上 `LogicWorldID` 和一组中继（relay）地址组成。其中手Q区有 601 条，微信区有 458 条，剩下十来条是抢先服、测试服和提审服。区服的后缀名基本都取自英雄称号或皮肤台词，比如落雪白狼和鲜血枭雄、电玩小子与长城防线。对比解析结果和游戏界面时还发现一个小细节，当时客户端列表里手Q区最高只显示到 547 区（落雪白狼，`LogicWorldID` 为 `1557`），但底层的 ilink 响应里其实已经一路排到了手Q600区（戍鼓铭心，`1610`），中间这五十多个尚未开服的大区名字早就下发到了本地，只是被界面过滤掉了。大区编号和内部 ID 大致遵循手QN区对应 `1000+N`、微信N区对应 `3010+N` 的规律，中间偶有跳号，比如 547 区对应 `1557`，原本的 `1547` 已经被其他内部节点占用了。

看清报文结构之后，下一步是怎么把改写逻辑塞进去。如果停留在网络层处理，可选的方案无非是挂载 libc 的收发函数、用 eBPF 拦截或者搭一套透明中继转发。我先写了段 Frida 脚本去挂 libc 的 `recv`、`read` 和 `recvfrom`，结果跑完 60 秒的启动流程，`tcpdump` 那边抓到了两千多次区服字段，而 libc 这一侧的命中计数始终是零。检查诊断日志确认脚本本身工作正常，进一步排查才发现，这条选服流量压根没经过 libc 封装，直接调用了 ARM64 编号为 207 的裸 `recvfrom` 系统调用。接着试了 eBPF，虽然在内核侧能稳定观测到完整的 ilink 流量特征，但真要在内核态做变长报文改写过于繁琐；至于搭透明中继，则意味着得把整套私有协议的拆帧与 TDR 解析、字段修改与重新组包以及心跳重传全部在外部重做一遍，为了改几个字段实在得不偿失。权衡之后，我决定直接放弃网络层，转进游戏进程内部去改已经解包出来的协议对象，这样无论底层网络走什么传输协议、加不加密，都不会影响上层的改写逻辑。

### 绕开 Frida 检测与手写 ARM64 Hook

进进程内部遇到的第一个阻碍是反外挂检测，这一点和前一个月做《[王者荣耀正式服 GM 调试面板与 CheatCode 验证记录](/2026/06/14/WZRY-GM-Panel/)》时遇到的拦截一致。最开始图省事直接用 Frida `attach` 主进程，结果每次一挂上去游戏就立即崩溃，注入进去的 `frida-gum` 运行时直接被检测逻辑中断。随后我又试着把 `frida-gadget` 塞进 Zygisk 模块里随进程启动加载，试图避开动态附加的特征，但主进程照样退出了，只有几个不包含目标协议对象的辅助子进程能存活下来。要想在主进程里强行保住 Frida，需要对抗的检测点太多，于是我干脆换成了纯 C++ 编写的 Zygisk 原生模块，跟着系统的 `zygote` 孵化过程直接进入游戏进程。这套方案可以稳定常驻，代价是没了现成的脚本运行时，底层的函数拦截（inline hook）必须自己动手解决。

在挑选原生拦截框架时，我先试了成熟的 ShadowHook。它的底层原理是用 4 字节的相对跳转指令覆盖函数头，这就要求中转跳板（trampoline）必须分配在距离目标函数 `±128MB` 的地址空间窗口内。平时这个限制根本不算问题，偏偏王者荣耀的 `libil2cpp.so` 体积高达 217MB，光是代码段（`.text`）就占了 155MB，而且经过 LTO 优化后排布得极其紧密，扫遍整个代码段只找到一处 12 字节的零填充，库映射附近也没有现成的空闲内存缝隙。ShadowHook 在安装时直接返回了 `errno=40`，翻看源码发现它试图拿目标地址减去 128MB 作为 `mmap` 的起始地址提示（hint），而这个位置正好撞在 `libil2cpp.so` 自身的映射区内，内核忽略提示后随机分配出来的内存超出了相对跳转的寻址范围；想自己找空洞用 `MAP_FIXED` 强行映射也行不通，因为每次启动 ASLR 随机化出来的内存布局都不一样。

既然 4 字节相对跳转走不通，我就改成了手写 16 字节的绝对跳转。具体做法是在目标函数开头直接覆盖写入 `LDR X17,#8; BR X17; .quad proxy`，把原本被覆盖掉的前几条指令搬到另一块通过 `mmap` 分配的可执行内存页里，执行完原指令后再用同样的绝对跳转跳回目标函数加 16 字节的位置。这套做法和早年的 And64InlineHook 思路一致，唯一的前提是被搬走的前 16 字节指令不能包含依赖当前 PC 的相对寻址指令（如 `adrp`）。好在我挑中的这几个目标函数开头都是标准的 `sub sp` 或 `stp` 栈帧建立指令，直接逐条搬移就能正常工作。

对于只在登录选服阶段调用的低频函数，趁着 `gcloud` 模块刚刚载入、网络还没建连的空窗期一次性写死这 16 字节跳转完全没问题。但到了协议收发口这几个从启动起就被网络线程高频调用的热点函数上，直接写 16 字节就不安全了，因为跨指令的非原子写入一旦在改写中途遇上网络线程正好执行到函数入口，就会读到撕裂的混合指令流，导致偶发崩溃。为了解决热函数的挂载安全，我把高频入口改成了断点拦截模式。安装时只用 4 字节对齐的原子写操作覆写一条 `BRK #0` 指令（机器码 `0xD4200000`），同时在进程里注册自定义的 `SIGTRAP` 信号处理函数，每次执行流撞上断点触发异常时，直接在信号上下文（`ucontext`）里把寄存器 `PC` 改写到我们的代理函数上。这种做法和 `frida-gum` 里的异常拦截器思路相同，虽然每次命中多了一次内核信号往返开销，但好处是随时都能原子挂载，不需要暂停其他线程。

在读写托管对象内存时，我还一并处理了两个底层细节。一是把所有的内存盲读操作统一改成了调用系统的 `process_vm_readv`，万一遇到无效野指针只会干净地返回 `EFAULT` 错误码而不会触发段错误把游戏搞崩，实测下来读取速度是通过管道（pipe）探测的四十倍左右；二是 ARM64 环境下托管指针的最高字节普遍带有 `0xb4` 之类的顶字节标签（TBI tag），在解析类型元数据之前必须先把高八位掩码剥掉。

## 运行时导出符号与定位协议收发口

### 从运行时内存还原 IL2CPP 符号表

底层的拦截机制准备就绪后，接下来得搞清楚目标函数到底在哪个偏移地址上。常规的静态分析流程是拿 `Il2CppDumper` 去跑安装包里的二进制和元数据，但在这个版本里，`CodeRegistration` 和 `MetadataRegistration` 两个核心注册结构的指针在磁盘文件上全被抹成了零，导致静态导出工具的自动与手动模式全部失效。

虽然静态入口被抹掉了，但从原理上讲，IL2CPP 作为一套把 C# 转成 C++ 再编译为原生 ARM64 机器码的 AOT 方案，它在运行时内存里依然必须维护一套完整的类型与方法元数据表，否则游戏自身的反射和序列化逻辑也跑不起来。想通这一点后，我直接在 Zygisk 模块里调用运行时的内部接口拿到当前 `domain`，顺着程序集（assembly）逐个枚举所有的类（class），把每个类的命名空间与父类名称、所有成员方法的名字与 RVA 偏移，以及每个实例字段的偏移量与类型名称全部遍历出来写进本地文件。整套导出逻辑在真机上跑完只用了不到一秒钟，游戏进程毫无卡顿，落盘生成了一份 69.8MB 的符号表文本，里面完整包含了 63,034 个类和 412,674 个方法，而且拿到的字段偏移直接就是当前 64 位进程里的真实内存布局。

### 拦截 HandleMsg 与 pack 并递归导出 JSON

有了完整的符号表，挑拦截点的原则就很明确了，尽量选在一处就能覆盖全部协议消息的总入口上。最开始改区服名那会儿，我挂的是构造服务器连接 URL 的具体业务方法，每次登录会触发一千两百多次，虽然能改名字，但换个功能就得重新找函数。翻看符号表里的协议封装层可以看到，所有出站消息的序列化都会经过 `CSPkg.pack`，而入站消息的反序列化则会经过 `unpack`。在这两个入口处可以直接拿到顶层的 `CSPkg` 容器对象，其中偏移 `+0x10` 是消息头指针，消息头内部 `+0xc` 存着核心路由键 `dwMsgID`；容器偏移 `+0x18` 是消息体指针，消息体内部 `+0x10` 指向的就是具体业务消息的数据对象（`dataObject`）。

不过实际挂上测试后发现，大厅阶段有一部分入站消息并没有走 `unpack`。顺着调用链继续往上查，最终确认收包侧真正的统一分发入口是 `NetworkModule.HandleMsg`，它的参数结构跟 `CSPkg` 完全一致，里面的 `msgid` 也一一对应。于是最终方案定为收包统一拦截 `HandleMsg`、发包统一拦截 `pack`。当时测试账号正好卡在爆满区服的登录重试循环里，日志里反复刷出 `1014`、`1191` 和 `1193` 三条消息，拿去跟游戏自身的日志输出一对，正好对应重新登录通知、游戏服重定向通知和错误码通知，证实前面梳理的这套结构体偏移完全准确。

在最初验证区服名改写时，我用的还是在消息体字节流里搜索特定字符串再做等长原地替换的土办法，「王者独尊」和「总裁牛逼」在 UTF-8 与 UTF-16LE 编码下字节长度恰好一样，这才侥幸跑通。要把改写做成通用能力，首先得摆脱对着十六进制盲猜字段的原始状态。既然进程里全套 IL2CPP 反射 API 都在，我就写了一段递归序列化逻辑，在拦截口通过 `il2cpp_object_get_class` 拿到消息对象的类型，顺着 `il2cpp_class_get_parent` 把父类链上的所有实例字段全部收集起来（注意必须通过字段的 `flags` 过滤掉静态字段，第一版忘了过滤时满屏打出来的全是 `BASEVERSION` 和 `CLASS_ID` 这类静态常量），再根据 `il2cpp_type_get_name` 逐层读出字段值并拼成 JSON。落盘后的单条记录长下面这样。

```json
{"dir":"r","msgid":1193,"cmd":"SCID_NTF_ERRCODE","type":"SCPKG_NTF_ERRCODE","body":
 {"stResultInfo":{"iResultId":11014,"stArgList":{"iNum":0,"astArgs":{"classId":148,
 "jarrCount":5}},"m_classID":150},"m_classID":3338}}
```

为了防止长消息被系统 `logcat` 截断或者在高吞吐时丢行，所有抓到的消息都直接写入独立的 JSONL 文件；遇到超大消息把单次缓冲区写满时，代码会自动补齐右括号并打上截断标记，确保落盘的每一行都是可解析的合法 JSON。把整套对象结构展开成明文 JSON 后，改写规则就可以直接填 `stResultInfo.iResultId` 这种直观的字段路径了。更关键的是，由于收包改写发生在 `unpack` 之后，改完的托管对象直接交给业务层消费，不再经过二次长度校验；发包改写发生在 `pack` 之前，底层的 TDR 序列化逻辑会自动按新数组重新计算长度前缀。统计全量 8,868 个协议类还能发现一个特点，这套协议里居然连一个 `System.String` 类型的字段都没有，所有 1,155 处文本字段清一色全用 `System.Byte[]` 字节数组表示。所以在对象层改写任何文本，本质上都是调用 `il2cpp_array_new` 分配一个新字节数组并把指针替换上去。

### 排查 Il2CppArray 的 8 字节偏移差异与对齐协议表

为了在界面上验证收包侧的变长文本改写，我换了一个没满员的区服登录进去，收到的消息种类立刻从卡登录时的 3 种涨到了 282 种，其中带文本 `Byte[]` 的字段有 21 个。我挑中了登录响应 `SCID_CMD_GAMELOGINRSP`（`1003`）里的 `szName` 字段，它在 TDR schema 里的定长是 64 字节，测试账号原本的昵称「饿了狂吃三碗」占 18 字节，进大厅后直接显示在左上角。

第一条测试规则我故意填了一个 78 字节的超长名字，日志里顺利打出了 `新 Byte[78](任意长)`，可切回游戏大厅一看，昵称位置竟然是一片空白。

![大厅左上角昵称位置空白，只剩等级](/upload/images/2026-07-26-WZRY-Protocol-Hook/nickname-blank.png)

起初我怀疑是 78 字节超出了 schema 的 64 字节上限被客户端丢弃了，于是立刻做了一个对照实验，把规则换成一个只有 15 字节的短名字重新登录，结果界面上照样是一片空白。这说明问题跟长度无关，是我们写入新数组的内存布局本身不对。为了看清真机上字节数组的真实结构，我在执行替换前先把原始 `szName` 数组从对象首地址算起的头 48 个字节原样打印了出来。

```text
+0x00  e08cdd496f0000b4                  klass
+0x08  0000000000000000                  monitor
+0x10  4000000000000000                  max_length = 0x40 = 64
+0x18  e9a5bf e4ba86 e78b82 e59083 ...   数据 = 饿了狂吃三碗
```

真相一看就明白了。常规文档里的标准 `Il2CppArray` 结构体布局是在 `+0x10` 放 `bounds` 指针并在 `+0x18` 放 `max_length`，真正的数组元素从 `+0x20` 开始，我第一版代码就是按这个标准偏移写的。但在这个版本的 `libil2cpp.so` 里，一维数组直接省掉了中间的 `bounds` 字段，`max_length` 提前到了 `+0x10`，正文数据从 `+0x18` 就开始了，整体往前缩了 8 个字节。旧代码按 `+0x20` 写入时，等于在字符串开头硬生生留出了 8 个字节的 `0x00`，游戏拿到手自然把它当成了空字符串。把数组读写的偏移修正为长度 `+0x10`、数据 `+0x18` 之后，短名字当场就正常显示了出来。

![大厅左上角昵称显示为「改写成功了」](/upload/images/2026-07-26-WZRY-Protocol-Hook/nickname-ok.png)

紧接着再把那条 78 字节的超长规则挂回去，就得到了文章开头那张显示着「任意长度改写验证」的截图。顺带我也测试了一下发包方向的超长数组替换，虽然换上 99 字节的新数组后游戏不会崩溃，但由于发包时的 `pack` 函数严格按照 schema 里的 `char szXxx[N]` 定长上限去截取字节，超出的部分并不会真正发往网络，所以任意长度改写目前只在收包侧成立。

光从内存里拿到数字形式的 `msgid` 还不够直观，最好能有一张完整的映射表把 `1193` 这种编号直接翻译成可读的命令名。正好此前有研究者公开过一份相邻小版本的协议整理成果，里面包含 4,015 条命令 ID 映射以及按 C# 类近似还原出来的 proto 与 TDR 定义。我抽查了心跳与登录、匹配以及商城和聊天等几组核心消息，核对发现命令编号、类名以及命名空间跟当前运行时的导出结果完全吻合，便直接拿来当路由字典用了。同时我也从自己导出的运行时符号表里筛出了全部 7,836 个协议消息类，把它们的字段名、类型与偏移导成了一份结构化 JSON 索引。这里处理过一个重名覆盖细节，同一个协议结构在符号表里往往同时存在 `CSProtocol.*` 和 `CSProtocolWrapper.*` 两套定义，前者才是运行时真正传递的引用类型，后者则是供特定场合使用的 ValueType 镜像，两者的字段偏移并不相同；建索引时必须使用包含命名空间的完整类名，否则很容易被 Wrapper 的偏移覆盖掉。

除了走 TCP 的 TDR 协议包，客户端里还有不少走 HTTP 的外围请求。为了把这批 URL 也记进日志，我最初尝试按导出符号去挂 `libcrosCurl.so` 里的 `cros_curl_easy_setopt`，结果每次启动只触发四次调用，传入的选项参数全都是 `99`（`CURLOPT_NOSIGNAL`），一条设置 URL 的调用都没抓到。进 IDA 看反汇编并顺着旁边的 18KB 插件库 `libPluginCrosCurl.so` 往下查才搞清楚，插件通过 `CurlFuncQueryService::QueryCurlFuncs` 向外提供了一张内部函数指针表，业务方全是拿着函数指针直接调的，挂外层的导出符号根本拦不到。看清这一点后，我不再执着于在设置参数时拦截，直接改挂两个库里的 `curl_easy_perform` 执行入口，一进函数就调 `getinfo(handle, CURLINFO_EFFECTIVE_URL)` 反查当前句柄里最终生效的完整 URL。这样改动之后，MSDK 和 FaaS 相关的完整带参请求，以及构造服务器地址时用到的 Tdir 串就全都顺利落进了 JSONL 日志里。

## 搭建主机消息工作台与远端字段改写

### 局域网常驻连接与关注集分流

早期只有几条测试规则时，直接写在手机端的 `wzry.cfg` 配置文件里还能应付。但等进入大厅看到多达 282 种不同的协议消息后，每次想试一个新字段都得先拉取 JSONL 文件翻结构、手动改配置文件再推回手机等热重载，来回折腾几次效率实在太低了。于是我干脆在电脑主机上搭了一套可视化的消息工作台，让手机上的 Zygisk 模块把拦截到的每条消息实时发往电脑，在网页前端里直接看实时流和查历史记录，支持全文检索，点几下鼠标就能生成并下发改写规则。

手机与电脑主机之间通过局域网的常驻 TCP 连接通信，协议格式是简单的 4 字节大端长度头加一帧 JSON 文本。这里必须显式开启 `TCP_NODELAY` 禁用 Nagle 算法，否则实测会在每次同步决策路径上凭空多出约 40ms 的等待延迟；同时模块内部的 socket 收发全部直接调用底层 syscall，避免数据流再次绕回我们自己挂在 libc 上的监测函数里。

在决定是不是让每一条消息都停下来等电脑端回话之前，我先在局域网环境下跑了一轮 300 次往返的延迟测试。实测常驻连接的 P50 延迟为 2.5ms，P99 为 5.0ms，最大单次耗时 18.1ms。单看几毫秒的往返似乎很快，但游戏在点击登录后的那一两秒峰值期内，每秒会密集收发多达 264 条消息；如果每一条都阻塞网络线程去同步询问电脑端怎么处理，一秒钟内网络线程累计要被卡住约 700ms，选服进大厅的过程会明显卡顿；相比之下，进入大厅后的空闲状态每秒只有约 5 条消息，累计等待 13ms 左右完全无感。

针对这个吞吐量特征，最终的设计是由主机服务端下发一份动态的「关注集（watchlist）」名单。只有命中关注集 `msgid` 的消息才会阻塞等待主机端的同步决策指令（支持 `allow` 原样放行、`patch` 按路径改写字段和 `drop` 在发包侧直接丢弃三种处置），不在名单里的其余消息在手机端直接放行，只走后台异步通道上报给前端展示。同时在手机端加上了保护熔断机制，一旦单次同步询问超时或者连续失败，模块会立即自动放行并进入十秒钟的熔断直通状态，之后再自动探活恢复，保证哪怕电脑上的服务端进程随时重启，手机里的游戏也不会卡死掉线。主机服务端直接用 Node 22 配合内置的 `node:sqlite`（开启 FTS5 全文检索）编写，单进程同时承载 TCP 决策服务、HTTP 控制接口与 Vite 加 React 构建出来的前端静态页面。

![工作台实时页，左侧消息流按 npc 过滤，右侧是消息详情和 body 的 JSON 树](/upload/images/2026-07-26-WZRY-Protocol-Hook/workbench.png)

上面这张图就是工作台的实时流页面。左侧列表支持按收发方向、消息号或接口名称实时过滤与暂停（图中正在按关键字 `npc` 过滤，筛出了消息号为 `2015` 的 `CSID_ADD_NPC_REQ` 请求），右侧上半部分展示包头元数据与运行时类名，下半部分则是展开后的消息体 JSON 树。在右侧的树节点上随便点一个字段，就能直接弹出规则编辑框并自动填好字段路径与当前值。

### 在工作台验证昵称和货币字段改写

工作台跑起来后，我先拿前面的昵称规则测试远端同步改写链路。刚切过来时踩了两个小问题，一是最初参照 30 字节空包的 P99 延迟把同步超时 `synctimeout` 设成了紧巴巴的 5ms，结果真正包含完整登录信息的事件 JSON 有 5KB 左右，设备端还没等主机回话就直接超时放行了，把超时阈值放宽到 50ms 后，日志里稳定打出了 `决策回话 8323us`；二是前端填的字符串在序列化时多包了一层转义引号，导致第一次改出来的昵称在屏幕上直接带上了双引号。

修完这两个细节，接下来试着改大厅顶部显示的货币数量。最开始我直接在实时流里全文搜索界面上显示的金币数字，结果一条都没搜到，原因是货币总额只在登录响应里下发一次，而我挂载工作台时游戏已经在大厅里了。改从协议结构索引里搜索带 `Coin` 字样的字段，很快就在 `SCPKG_CMD_GAMELOGINRSP`（`1003`）里找到了 `stCoinList.CoinCnt`，类型是一个 `UInt32[]` 整型数组。为了支持修改数组里的特定元素，我给底层的 JSON 遍历器补上了数值数组展开逻辑以及 `name[idx]` 下标路径语法。

退回登录页重新点一次「开始游戏」触发完整的 `1003` 响应后，工作台里抓到了 `stCoinList.CoinCnt[1] = 6222`，跟账号界面上显示的金币数分毫不差；同时下标 `6` 的数值是 `190`，正好对应界面上的钻石数量。需要注意协议参考仓库里的 `COM_COIN_TYPE` 枚举在这里只能做大致参考，真正准确的数组下标含义需要跟界面数值做一次交叉确认，前端也会把确认过的下标含义保存下来。在工作台弹窗里给下标 `1` 和 `6` 填上两行 `patch` 规则。

![规则编辑弹窗，配置收包 msgid 1003 与两条 patch 字段路径](/upload/images/2026-07-26-WZRY-Protocol-Hook/rule-editor.png)

保存规则后重新登录进大厅，顶栏的金币和钻石就变成了我们填进去的数值。

![大厅顶部显示金币 8888万、钻石 66666](/upload/images/2026-07-26-WZRY-Protocol-Hook/coins.png)

至于点券则没有放在 `CoinCnt` 数组里，它有自己独立的通知消息 `SCPKG_CMD_ACNTCOUPONS`（消息号 `1161` 与 `1162`），核心字段叫 `llCouponsCnt`，实测用同样的路径规则也能直接改掉。当然，到这一步为止改的都还只是客户端本地反序列化出来的显示对象，服务端的真实账本一分钱都没变，如果拿着改出来的这几千万金币去商城点购买，服务端校验完余额照样会返回失败。

## 本地消息注入与客户端购买链路分析

### 按 msgid 分发的总线机制与本地构造 CSPkg

在做工作台的前端消息列表时，我本来想加一列「请求往返耗时（RTT）」，这就需要把客户端发出去的请求和服务端回来的响应配成对。结果翻遍了协议头和分发代码也没找到通用的请求上下文 ID。去看游戏的注册与分发实现才明白，`RegisterMsgHandler(msgid, delegate)` 内部维护的路由表完全只按 `msgid` 建索引，收包入口 `HandleMsg` 拿到包头里的 `msgid` 查出对应的委托函数就直接调过去了，整条链路里既没有逐请求的回调闭包，也没有通用的关联令牌。

我也核对了包头里的其他序号字段。`CSPkgHead.dwSvrPkgSeq` 是服务端给下行包编的序号，客户端在随后发出的上行包里原样回显最近收到的那个值，同一个序号会连续出现在好几条不同的发包里，而服务端主动推送的通知包里这个值固定为 `0`，本质上是一个确认（ack）流水号；全量四千多个协议类里只有 6 个新接口定义了 `dwClientReqID`；而且服务端下行消息（SCID）有 2,435 个，客户端上行消息（CSID）只有 1,580 个，大量服务端主动推送的通知本来就没有对应的请求。所以工作台里的耗时列最后只能靠 `CSID_X_REQ` 与 `SCID_X_RSP` 的命名规则加时间窗口去近似配对（1,580 个 CSID 里能配上 1,280 个），并在界面上标明是推测值。

不过这套纯粹按 `msgid` 认领消息的总线机制，反过来给本地消息注入提供了极大的便利。既然 `HandleMsg` 根本不检查这条消息是不是真的对应某次网络请求，那只要我们在本地进程里按照合法的内存布局凭空构造出一个 `CSPkg` 对象，再直接塞进 `HandleMsg` 的入口，客户端业务层就会按真实服务器推送的标准流程去处理它。

真正动手写本地构造逻辑时，主要解决了对象初始化和执行线程两个问题。外层的 `CSPkg`、`CSPkgHead` 和 `CSPkgBody` 三个容器类每次收包都会经过，直接在拦截函数里把它们的类指针缓存下来即可；内层真正的业务协议类（`dataObject`）因为可能从来没在真实流量里出现过，需要拿着类名遍历 112 个程序集调用 `il2cpp_class_from_name` 动态查找。调 `il2cpp_object_new` 分配出实例内存后，必须紧接着调一次 `il2cpp_runtime_object_init` 去执行 TDR 自动生成的 `.ctor` 构造函数，把内层的嵌套子结构体和定长数组全部初始化出来，否则内层引用字段全是空指针，业务代码一读就会崩溃。

线程方面，IL2CPP 的托管 API 必须在已经附加（attach）到运行时 domain 的线程上调用，我最开始直接在自己的后台轮询线程里调构造接口，游戏进程当场就退出了。后来的改法是把主机发来的注入指令先放进一个本地线程安全队列，等游戏自身的网络线程下一次触发 `HandleMsg` 时，在分发当前真实消息之前先把队列里的待注入消息在当前网络线程上就地构造并分发掉。大厅状态下每秒都有常规消息经过，排队延迟几乎感知不到，而且赶在当前 `_RSP` 响应分发之前清空注入队列，刚好符合真实服务端「先推资产变更通知、后回操作确认响应」的时序。先拿两条简单的消息做注入验证，往客户端凭空推一条 `1162 SCPKG_CMD_ACNTCOUPONS` 并把 `llCouponsCnt` 填成 `777777`，大厅顶栏的点券数字立刻变成了 `777777`；再推一条 `1823 SCPKG_HEROSKIN_ADD`，商城里对应皮肤下方的按钮当场就从「购买」切换成了「已拥有」。

### 拆解购买时间线、英雄拥有列表与脚本模块

跑通单条消息注入之后，我想试试能不能在本地完整模拟一次商城购买的客户端表现。为了搞清楚真实购买时服务端到底下发了什么，我先拿金币买了一个英雄小乔，把这一瞬间客户端收发的全部报文按顺序记录了下来。结果一条 `1817 CSID_BUYHERO_REQ` 购买请求发出去，服务端一口气连回了七条消息。

```text
s 1817 CSID_BUYHERO_REQ                  dwBillNo=... bBuyType=2 dwHeroID=106
r 1010 SCID_ACNT_INFO_UPD                货币扣除
r 1504 CSID_TASKUPD_NTF                  任务进度
r 48601 SCID_COLLECT_VALUE_TOTAL_INFO_NTF
r 4403 SCID_ACHIEVEMENT_DONE_DATA_CHG_NTF
r 1810 SCID_HERO_INFO_UPD          ←     英雄到账，排在 _RSP 前面
r 1818 SCID_BUYHERO_RSP                  iResultId=0 dwHeroID=106 dwCoinCost=5888
r 51457 SCID_BUY_REGRET_INFO_NTF         反悔期信息
```

注意看上面的顺序（第 6 条 `1810 SCID_HERO_INFO_UPD` 排在第 7 条 `1818 SCID_BUYHERO_RSP` 之前），真正的英雄到账通知是赶在购买成功响应之前先落地的。对比之下，点券不足去点购买皮肤失败时，服务端只会孤零零地回一条 `1820` 响应，里面带着错误码 `iResultId=13`，而且扣费类型 `wCoinType` 和金额 `dwCoinCost` 都是 `0`。如果这时候我们只配一条静态规则把 `1820` 的错误码硬改成 `0`，客户端因为根本没收到前面的资产到账通知，并不会弹出购买成功界面。

而当我们先用注入队列把 `1823` 皮肤到账通知塞给客户端、再把 `1820` 的响应结果码改成 `0` 之后，购买成功的获得界面确实弹出来了，客户端紧接着会自动向服务端发出穿戴新皮肤的请求，然后被真实服务端拦下来。

```text
s 8566 CSID_CMD_SKIN_SUIT_REQ         客户端自动发的穿戴请求
r 8569 SCID_CMD_WEAR_SKIN_SUIT_RSP    iResultId=122009
r 8567 SCID_CMD_SKIN_SUIT_RSP         iResultId=0
```

上面返回的错误码 `122009`，对应的就是下面这张截图里的文字提示。此时商城里的按钮已经变成了「已拥有」，但自动穿戴那一步因为服务端发现账号实际并未拥有该皮肤而被拒了。

![商城里皮肤按钮显示已拥有，上方提示由于您尚未拥有翡翠华章皮肤，无法自动穿戴](/upload/images/2026-07-26-WZRY-Protocol-Hook/skin-owned.png)

所以要想让这次皮肤购买在客户端本地走完整个流程，一共需要三处配合，先注入 `1823` 到账通知，再把 `1820` 购买响应和 `8569` 穿戴响应的结果码都改成 `0`。另外在写注入逻辑时还核对了一下资源编号的换算规则，客户端发出的购买请求里只带一个合并后的 `dwResID`，而到账通知里要求的则是拆开的英雄号 `dwHeroID` 与皮肤序号 `bSkinID`，两者的换算关系是 `dwHeroID = dwResID / 100` 和 `bSkinID = dwResID % 100`，比如资源号 `18801` 就对应 188 号英雄的 1 号皮肤。

顺着同样的方法去模拟买英雄时，又发现了另一处数据源差异。注入 `1810 SCID_HERO_INFO_UPD` 到账通知后，虽然购买成功的弹窗出来了，但切回商城列表一看，那个英雄依然显示为未拥有。排查后发现，`1810` 只负责对已有英雄条目做增量状态更新，而整个账号的英雄拥有列表是在登录阶段通过 `1886 SCID_ACNTHEROINFO_PARTTWO_NTY` 下发的，里面是一个 `dwHeroNum` 计数（测试号当时为 `12`）配一个长度 200 的数组。如果登录下发的这张总表里没有这个英雄，光发增量更新商城是读不到的。解决办法是在拦截到 `1886` 登录通知时，把 `dwHeroNum` 加一，并往后面的空槽位里按元素类型动态补建一个英雄对象写进去。

写到这一步，原本只能在表单里填固定值的静态规则显然就不够用了。因为模拟购买既要从上行请求里动态读取 `dwResID` 做整除和取模运算，又要跨消息记住当前会话已经发过哪些英雄好在下次重登收到 `1886` 时自动补进列表，还得主动往注入队列里推新消息。于是我在主机服务端里加了一套基于 `node:vm` 的轻量脚本模块系统，在脚本上下文里暴露了消息对象 `msg` 与 `body`，同时提供字段读写与推送方法 `get`、`patch` 和 `push`，以及持久化与日志接口 `store`、`grants` 和 `log`，用 `on` 声明触发条件、在 `handle` 里写处理逻辑。比如处理皮肤购买到账的模块核心代码只有十来行。

```js
on = { dir: 's', msgid: 1819 };
handle = function (ctx) {
  const resid = ctx.get('dwResID');
  ctx.push({ msgid: 1823, type: 'SCPKG_HEROSKIN_ADD', patch: [
    { path: 'dwHeroID', value: String(Math.floor(resid / 100)) },
    { path: 'bSkinID',  value: String(resid % 100) },

```

脚本里的状态存储分成了两层，`ctx.store` 是模块私有的键值存储，`ctx.grants` 则是按物品类型分类的全局发放台账，工作台前端专门做了一个存储管理页用来直接查看和手动增删台账记录。日常简单的固定字段替换依然用直观的表单规则，遇到需要动态计算、跨消息维护状态或者主动推送新消息的场景就交给脚本模块处理。

## 尾声

最后明确一下这套工具目前的验证边界。文中所做的全部字段改写与本地消息注入，本质上都只是在当前客户端进程的内存里修改反序列化后的对象状态。无论是改出来的金币、钻石和点券数字，还是通过注入到账通知解锁的英雄与皮肤显示状态，都只停留在当前客户端会话的 UI 与本地逻辑层；一旦切换场景触发重刷或者重新登录，服务端下发的真实数据就会把本地状态重新覆盖掉，服务器上的账户数据自始至终保持原样。

如果要往完整的本地模拟服务端方向走，还需要把整套持久化状态、业务计算和校验逻辑全部在服务端实现出来。另外文中涉及的所有 IL2CPP 函数 RVA 偏移都严格对应国服 `11.4.1.1`（`2026-06-14` 构建）这一版二进制，客户端更新后需要重新运行导出脚本定位。基于这套进程内协议拦截与 JSON 递归序列化通道，几天后我又顺着战绩查询接口做了一轮大规模样本统计，具体分析结果整理在下一篇《[我分析了 11 万局王者荣耀对局中的伪人与匹配机制](/2026/07/28/WZRY-Analysis-2/)》里。
