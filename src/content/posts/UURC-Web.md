## 前言

很久没写这种长篇逆向记录了，最近动手做了一个新项目 [UURC-Web](https://github.com/iola1999/uurc-web)。起因是公司电脑出于安全策略不允许安装第三方远控客户端，但我坐在工位上偶尔还是得连回家里那台 Mac 处理点事情。既然桌面客户端装不了，最省事的办法就是直接用浏览器解决。

网易 UU 远程（UURemote）在 macOS 上的延迟很低，画质表现也不错，只是官方一直没有提供网页版主控端。于是我给 AI 接上了 IDA Pro MCP，提出把 UU 远程的主控协议搬进网页的需求。接下来几天里，我主要负责准备调试环境、描述实机现象和验收结果，让 AI 顺着官方客户端的二进制符号把这套协议一层层抠出来。我当时的目标很明确，只要一个单页网页能完成短信登录和画面预览，能正常使用键盘鼠标操作，并且能把信令中转服务部署进 Cloudflare 的基础无付费配额里，同时保留 WebRTC 局域网与 P2P 直连能力就够了。

## 拆解客户端与对齐 WebRTC 协议

### 拆解 Android 客户端与定位协议分层

动手的头一步是摸清官方客户端的通信流程。我把 Android 版的 `com.netease.uuremote` 安装包交给 AI，先用 `apktool d` 解包。翻看反编译出来的代码可以发现，外围的账号登录与设备列表管理基本都在 Java 和 Kotlin 层实现，走的是常规的 HTTPS 请求（网易 `nrd` API），而核心的音视频流、信令（Signaling）和 WebRTC 协商逻辑，全都放在原生库 `libstreamer.so` 里面。

协议分析的主要工作量也集中在这个原生库里。AI 通过 IDA Pro MCP 顺着导出符号和交叉引用往下查，陆续定位到了 `socket.io` 和 `SDP`、`ICE` 与 `DTLS/SRTP` 相关的处理函数，最终把整个通信架构梳理成了业务 API、Socket.io 信令和 WebRTC 数据通道三层。

### 对齐原生客户端的 WebRTC 通道与信令封包

摸清分层之后，下一步是在浏览器里复刻它的建连过程。原生客户端在底层会一次性创建 5 路 `video` 收流通道和 1 路 `audio` 通道，纯浏览器端要严格对齐这套通道布局，前期的协商参数调了不少轮。

除此之外，UU 远程的信令层在标准 WebRTC 交换外面还包了一层名为 `SOAC`（Signaling Offer/Answer/Candidate）的自定义结构，并且会用 Gzip 压缩 SDP 字符串来缩减报文体积。受控端只认这套固定格式，AI 便对照着原生客户端的反编译逻辑，在前端手工构造了一致的 Protobuf 风格封包（Envelope）和二进制载荷。等跑通 `video/rtx` 重传协商，再补上官方客户端每 100ms 发送一次的 `SendEchoRequest` 保活心跳之后，第一版网页端终于能稳定挂着远端桌面看画面了。

## 开源后的几轮体验与输入排查

### 鼠标一动画面就停推的根因

项目刚开源那会儿，碰到过一个很反常的现象。如果只挂着网页看远端屏幕，视频流可以一直正常播放，可一旦移动鼠标接管控制，几秒钟后画面就会彻底卡住，必须断开重连才能恢复。去查浏览器的 WebRTC 统计信息，状态显示为 `transport_stalled`，底层的 RTP 收包已经彻底停了，说明受控端直接中断了推流。

顺着调用链排查下来，问题出在前端的输入热路径上。旧代码里每次触发 `pointermove` 事件，都会连带触发大约三次整棵 React 组件树的重渲染，中间还要深拷贝一份完整的会话状态。鼠标以 60 到 120Hz 的频率连续移动时，浏览器主线程几乎全被 React 渲染占满，导致每 100ms 一次的控制心跳和 `EchoRequest` 回复不断延迟。更糟的是，`channel.send` 偶尔遇到发送缓冲区背压时，异常处理逻辑还会把心跳定时器直接停掉。受控端长时间收不到心跳，直接把主控端判定为离线并切断了视频流。

找到原因后，AI 把调试事件改成了环形缓冲区存储，让 data channel 的状态只在真正发生变化时才通知 React，同时把高频输入处理从主控制器里独立拆了出来。我在实机上反复移动和点击鼠标，把还会卡顿或丢落点的边界情况继续反馈回去。随后它又把连续的鼠标移动合并为每个动画帧（`requestAnimationFrame`）只发送一次，并在点击事件触发前先补发一次当前坐标，这样节流合并后也不会弄丢点击瞬间的真实落点。

为了方便后续继续观察，我们还把卡顿诊断拆细了。`transport_stalled` 代表底层 RTP 收包已停，而 `decode_stalled` 代表数据包还在正常进入浏览器、但解码帧数不再增加。后者连续出现两次时会触发自动恢复，同时在控制台记录 RTP 增量、ICE candidate pair 和信令状态，后续再遇到卡顿就能直接看现场数据。

### Windows 受控端键鼠无响应与按键连发

解决了画面停推之后，紧接着遇到的是 Windows 受控端只能看画面、鼠标和键盘完全没有反应的问题，而且浏览器控制台里没有任何报错。我把一台 Windows 受控端和官方 Android 主控端连好，让 AI 重新翻查 `libinputmanager.so` 并对照控制通道的抓包数据。对比后发现，桌面端受控的输入通道直接接收 JSON 报文，而 Android 和 MuMu 模拟器受控端则需要在外面额外包一层 `send_to_rom` 的 Protobuf 结构。当时的代码把 Windows 受控端误送进了移动端封装路径，被控端收到格式不对的报文后直接静默丢弃了。

除了外层封装，鼠标坐标和键盘键码也各有一层转换逻辑。Windows 与 macOS 受控端都接收 `[0, 1]` 区间内的归一化绝对坐标，而早期代码发送的是原始像素值；键盘输入则需要先把浏览器事件转换成 Android KeyCode，再映射成 Windows 的虚拟键码（VK），同时带上官方报文里的 `interrept: true` 标记。把分发路由、归一化坐标和键码映射全部补齐后，Windows 端的键鼠操作终于有了响应。

不过刚能打字，马上又碰到了敲入 `whoami` 会变成 `whoooooami` 的连发问题。原因在于网络抖动拉长了 `kbd_press` 到 `kbd_release` 两条报文之间的时间间隔，UU 的 Windows 服务端把中间这段网络延迟直接当成了用户长按按键。最终的改法是把修饰键和普通键拆开处理，让 Ctrl 和 Alt 以及 Shift、Meta 这类修饰键保持按下状态直到浏览器触发 `keyup` 再释放，而普通字符键在每次 `keydown` 触发时立即连发一组 press 加 release，真正的长按重复则交给浏览器自身的 `repeat` 事件去驱动。至于中文输入，直接调用远端系统的输入法即可，跨端复制粘贴则走独立的文本通道。

### 右键菜单拦截、切窗口卡键与滚轮手感

基础输入走通以后，日常高频使用中又暴露出不少影响手感的细节问题。最典型的是在浏览器里按右键弹出系统菜单时，菜单会拦截掉后续的 `pointerup` 事件，导致远端系统一直认为鼠标右键还按着不放；平时按 Alt+Tab 切换本地应用或者切换浏览器标签页时，页面同样收不到对应的 `keyup` 事件。为了解决这类卡键现象，我们在画布失焦、窗口 `blur` 以及页面隐藏（`visibilitychange`）时统一挂上了 `releaseAllInputs` 清理逻辑，把当前记录在案的所有按下按键和鼠标按钮全部补发一次抬起。

滚轮和触控板的适配也调了好几轮。React 默认的 `onWheel` 是被动监听器（passive listener），里面调 `preventDefault` 拦不住外层网页跟着一起滚动，所以远控画布区域改成了手动绑定原生的非被动监听器。桌面端还需要把 DOM 的内容滚动方向反转为 UU 协议使用的原生滚轮方向，并把 pixel、line 和 page 三种滚动增量单位做统一换算。针对 Mac 触控板双指滑动容易带出横轴抖动的问题，前端会先滤掉微小的横轴噪声，再把滚动增益系数压到 0.5，这样手指轻轻一划就不会直接翻出去大半页。

在多显示器产生多路视频轨的场景下，早期代码简单调用 `querySelector("video")` 取到了第一路隐藏的视频元素，导致鼠标坐标一直按错误的分辨率在换算。现在改成了精确匹配当前正在显示的视频流，并复用同一套几何计算同时处理 `contain` 留黑边和 `cover` 裁切两种显示模式。

## 近期补齐的连接、光标与远控细节

到七月份这一版，整个连接建立和日常交互流程又顺畅了不少。现在点进设备控制页后，前端会自动加入设备并完成 WebRTC 建连，等控制通道一打开就直接切进「控制中」状态，并把键盘焦点自动落到远控画面上。如果目标设备恰好被自己上一个还没超时的网页会话占着，前端会比对参与者的 `clientId` 自动完成无缝接管；只有在占用者是其他端或他人时，页面才会停下来弹窗等待确认。遇到网络环境不佳、自动直连路径连续重连失败两次时，第三次重连会自动切换为强制走 UU 官方 Relay 中转。

除了控制自己的设备，伙伴远程协助功能也接了进来。登录后输入对方的设备 ID 就能发起连接，前端会先查一遍受控端开启的验证方式。只需要验证码的设备会直接带码加入，需要对方手动点同意的设备会停在等待状态，两项验证同时开启的设备也能按顺序走完流程。握手成功后接口会返回目标系统的平台类型，由页面自动切换成对应的 Windows 或 macOS 输入协议。

界面与声音细节也做了一轮收尾。视频源切换菜单里直接标出了各路画面的分辨率和「无信号」状态，切到空视频轨时会给出「该画面暂无内容」的文字提示，不用再对着黑屏猜原因；顶部的命令栏平时固定停靠在画面上方，切进全屏模式后才会变成可自由拖动的悬浮条；音频改由独立的播放器组件输出，支持在工具栏里随时静音或调节音量，遇到浏览器策略拦截自动播放时也会在按钮上提示手动恢复。

在这批改动里，远端光标同步对实际操作手感的改善超出了我的预期。以前盲点远端桌面时，鼠标移到输入框、窗口边缘或者超链接上没有任何反馈，现在控制通道里的 `cursor shape` 消息会被实时解析成本地光标状态，无论是文本输入和等待，还是移动、窗口缩放与手型点击，都能跟着远端系统的真实状态即时变化，远端发来的自定义 PNG 图标也会完整保留原有的热点偏移和缩放比例。在桌面浏览器上操作时优先调用原生光标渲染，到了触摸屏设备或不支持自定义图片光标的环境里，页面会自动回退为一层跟随指针移动的画布光标，并且和鼠标输入共用同一套画面几何换算，哪怕切换视频源或者留有黑边，光标尖端和实际落点也严格对齐。

双向剪贴板也一并打通了。本地复制后在网页里粘贴，文本会通过独立通道直接发往远端；受控端复制内容后回传的 `RomMsg_Text` 消息则会自动写入浏览器剪贴板，如果遇到浏览器权限拒绝自动写入，文本也会保留在侧边面板里方便随时手动复制。

## 在线体验与自部署说明

经过这两个月的陆陆续续修补，我平时已经把 [UURC-Web](https://github.com/iola1999/uurc-web) 当成主力工具在用了。从短信验证码登录、账号凭证导入导出，到设备在线状态查看以及 Windows 和 macOS、Android 与 MuMu 模拟器的多平台远控输入，都已经能在网页里稳定跑通。

如果你想先看一眼界面长什么样、走一遍基本流程，可以直接访问我搭的公共实例 [https://uurc.678234.xyz](https://uurc.678234.xyz)。不过由于网页端需要经手短信登录、账号凭证以及带鉴权的业务 API 请求，如果打算作为日常远控工具长期使用，还是建议自己在本地或私有账号下部署一份，把输验证码和导入凭证的操作留在自己完全可控的环境里。

自部署支持 Docker 容器直接拉起，也支持部署到 Cloudflare Worker 配合 Durable Objects 运行。后者正好能放进 Cloudflare 提供的无付费基础配额里，平时几乎没有维护成本。在这个架构下，Worker 只负责托管静态页面、转发业务 API 请求以及充当信令网关，真正占带宽的画面、声音和键鼠输入依然由浏览器通过 WebRTC 与受控端直接协商。默认策略会优先尝试局域网或公网 P2P 直连，只有在打洞条件不满足时才会回退到官方中转，所以把服务端挂在海外的 Cloudflare 节点上并不会拖慢直连控制时的画面延迟。

## 尾声

回头看这个项目，最花精力的地方其实是把原生库 `libstreamer.so` 与 `libinputmanager.so` 里的调用链、私有封包字段跟浏览器端的 WebRTC 实现逐项对齐。几万行反编译伪代码如果全靠我自己肉眼去硬啃，进度会非常慢。这次给 AI 配上 IDA Pro MCP 之后，它在二进制符号检索和结构还原上的效率明显比我高得多，而我则把精力放在描述实机复现现象、判断它的排查方向有没有跑偏以及上真机做最终验收上。这种分工配合在逆向工程与协议复刻类项目里确实非常省心。

项目代码目前已经在 GitHub 开源，如果你平时也经常碰到受限环境下连回家里电脑的需求，或者单纯对这套混合了自定义信令的 WebRTC 远控协议感兴趣，可以直接去仓库里翻看源码。最后还是照例提醒一句，本文记录的所有逆向分析、抓包调试与远控验证均在个人账号及自有设备上完成，相关代码与方法仅限在自己拥有或取得明确授权的设备间使用，请勿用于未授权连接或规避所在组织的安全管理规范。
