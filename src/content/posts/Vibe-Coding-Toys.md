## 前言

刚写完一篇 [UURC-Web](/2026/05/18/UURC-Web/) 的逆向记录，顺便回头盘点了一下今年开过的业余项目，才意识到这几个月下来我自己几乎没怎么亲手敲过业务代码。

我现在跟 AI 配合的节奏已经很固定了，平时由我口头描述目标需求或者实机上看到的异常现象，AI 负责翻资料、改代码和跑排查脚本，我只管盯着运行结果拿真机验收，一旦发现方向跑偏就及时叫停重来。白天上班写业务代码慢慢变成了这种分工，到了晚上折腾自己的业余项目就更彻底，基本上全靠自然语言推进。下面这五个项目，就是最近下班后靠这种模式陆陆续续做出来的。

## UURC-Web 与网页端远控协议复刻

[UURC-Web](https://github.com/iola1999/uurc-web) 是这批项目里我自己用得最频繁的一个。公司电脑不允许安装第三方远控客户端，我就动了在浏览器里把网易 UU 远程主控端复刻出来的念头。这件事如果放在以前完全靠手写，先得解包 Android APK、对着原生层的 `libstreamer.so` 读反编译伪代码，还得把那套加了自定义信令封装的 WebRTC 协议逐个字段对齐，光是前期调研就得耗掉好几个周末。

这次给 AI 接上 IDA Pro MCP 之后，它可以直接进到原生库里翻查 Protobuf 封包结构、顺着引用链找加密密钥。整个项目里最难查的一次卡顿出现在开源之后，当时只看远端画面一直很稳定，可只要一动鼠标接管控制，几秒钟后视频流就会彻底停推。排查下来是因为每次 `pointermove` 事件都会连带触发三次左右的整棵组件树重渲染，导致 100ms 一次的控制心跳被主线程拖慢，遇上 data channel 发送背压时旧代码还会把心跳直接停掉。后来 AI 把调试事件改成环形缓冲、把输入处理从主控制器里拆出来，并将连续的鼠标移动合并到每个动画帧只发一次，才彻底解决了断流问题。

Windows 受控端的键鼠输入后来也单独返工了一轮。桌面端直接接收 JSON 报文和 `[0, 1]` 区间内的归一化坐标，键盘使用 VK 虚拟键码；遇到网络延迟偏高时，受控端会把按下到抬起之间的时间差当成用户长按，敲一个 `whoami` 会被打成 `whoooooami`。调整后的逻辑改在每次 `keydown` 时立即连发一组 press 加 release，只把修饰键留到 `keyup` 再释放。如今控制页已经支持自动建连和连续重连失败后自动切 UU Relay，伙伴远程协助也能处理设备验证码与对端确认，音频播放、双向剪贴板以及跟随输入框和窗口边缘变化的自定义热点光标也全都接了进来。整个过程里我基本只负责描述实机现象、抓日志和验收，具体的代码改动都交给了 AI。

## SmallDesktopDisplay 与单片机远程渲染

第二个项目 [SmallDesktopDisplay](https://github.com/iola1999/SmallDesktopDisplay) 是一个基于 ESP8266（ESP-12E）的桌面迷你显示器。以前玩这类小内存单片机，总得自己写 C++、调 SPI 屏幕驱动，还要对着可怜的几十 KB 内存精打细算地抠像素。

这次我让 AI 直接按远程渲染架构来设计。板子上的 ESP8266 固件只负责选择通信链路、上报物理按键事件，以及把收到的 RGB565 矩形差分帧刷到 TFT 屏幕上；所有 UI 排版、页面状态流转和动画渲染全部放在后端的 `remote-render` 服务里运行，由 Node.js 配合 React、Yoga 和 Skia 实时生成 `240x240` 分辨率的画面。把渲染逻辑挪到后端以后，给小屏幕加功能就跟写普通前端页面没什么区别了。目前主界面是时钟加天气，公历旁边会同时显示农历、节气与节日，主题、字体和屏幕亮度既可以在设备上按键调节，也能直接从 Web 控制台实时预览。早期塞进去的贪吃蛇、吃豆人和打砖块小游戏后来被我删掉了，实机上显得过于杂乱的数字雨背景也一并移除。去掉这层高频动态背景后，稳态传输量直接减半，全屏重同步的数据量从 28KB 降到了 9KB。

真正接上硬件实机后，还是碰到了不少只有肉眼能看出来的显示问题。比如网页预览图里看着很正常的配色，刷到 ST7789 屏幕上会明显发灰，Noto 字体渲染出来的天气图标在垂直方向上也比旁边的文字高出了 5 到 10px。我把实拍现象反馈给 AI，它在服务端输出阶段加上了饱和度与暗部 gamma 补偿，又用真实字体文件逐像素测量字形墨迹边界，把图标的垂直偏差压到了 2px 左右。

为了进一步压低刷屏延迟，底层传输链路也重做了一遍。设备插上电脑 USB 时，会在开机后的 1.5 秒窗口内主动探测宿主机，一旦握手成功就切到 921600 波特率的串口推送画面，没探测到宿主机则继续走 WiFi。因为我这台 Mac 上的 OrbStack 容器没法直接透传 USB 串口，渲染服务后来也顺带改成了宿主机上的 launchd 常驻进程。算上相邻差分色块合并、CRC32 改查表计算，以及把 TFT 的 SPI 时钟从 27MHz 提升到 40MHz，平时时钟跳秒通常只需要传输一个 747B 的小矩形；最近一次实机测下来的全屏帧体积是 8.9KB，整帧刷完耗时 128ms。

顺带一提，串口模式刚上真机那会儿还出过两个很隐蔽的时序问题。我把串口日志丢给 AI 排查，它很快定位到健康检查在拿旧的 `millis()` 时间戳做无符号减法，导致数值下溢成了约 42 亿，触发设备每两秒误发一次探测包；同时从 WiFi 切换到串口时，WiFi 模块的反初始化阻塞了主循环，导致涌入的第一帧画面直接撑爆了 4KB 的串口接收缓冲区。随后它把时间戳读取改在消费完整帧之后，并在关闭 WiFi 完成前暂缓回复握手，宿主机收到设备重启发来的 `HELLO` 也会立即重置状态回应，串口链路这才彻底稳住。

## x-tui 与终端全屏刷推工具

[x-tui](https://github.com/iola1999/x-tui) 是我为了替代臃肿的官方网页版而做的 X（Twitter）终端客户端，运行在终端的 Alt-buffer 全屏模式下。

这个项目的依赖组合比较跨界，底层基于一份 fork 出来的 `@anthropic/ink`，再用 React 19 配合 Bun 直接跑在终端里。日常操作完全对齐 Vim 的键位习惯，用 `j/k/gg/G` 上下移动，按 `l/t/b` 完成点赞、转推和收藏，按 `/` 呼出搜索，从推文详情页退回时间线列表时还会通过 SWR 缓存保留原来的列表内容和焦点位置。

除了纯文本，推文里的配图也能直接在终端里渲染出来。遇到 iTerm2、Kitty 和 Ghostty 这类现代终端时会直接调用各自的原图显示协议，碰到不支持图片协议的终端则自动回退成半方块（Halfblock）字符画。整个开发过程里我完全没去管底层复杂的终端控制序列和光标位置跟踪，只是提了一句想按 Vim 的操作方式在终端里刷推并发图，剩下的渲染和状态管理代码全由 AI 生成了出来。

## AnchorDesk 与带引用溯源的资料库

前面几个都偏个人玩具，而 [AnchorDesk](https://github.com/iola1999/AnchorDesk) 做出来的完成度已经接近一个正经的产品原型，主要给个人或小团队用来整理和检索本地工作资料。

它支持导入 PDF 与 Docx、TXT 和 Markdown 文档，切块解析后存入本地检索库。和普通聊天前端最大的区别在于强制要求先给依据再给结论，每次回答都必须附带文档内的具体段落引用，本地资料库里查不到对应信息时才会主动去公网搜索补充。项目里相对繁琐的 BullMQ 异步任务队列调度、Drizzle ORM 的数据库 Schema 迁移，以及长篇报告大纲生成与分章节导出逻辑，同样全是靠自然语言对话一路生成的。算下来我在这个仓库里亲手写过的文字，大概只有 README 里那句「本项目采用 MIT 协议」。

## Lapse-box 与旧手机延时摄影流水线

最后一个项目叫 Lapse-box，目前还没整理开源，专门用来把手头闲置吃灰的旧 Android 手机改造成全自动延时摄影机。

虽然表面上看只是定时拍照，但后台其实串起了一整套自动化处理流水线。固定在窗台上的旧手机在拍摄前会执行连续焦点扫描，并自动测试不同 ISO 档位下的曝光度与底噪矩阵；后端的常驻脚本则负责定时从手机拉取原始照片、执行批量降噪，最后调用 FFmpeg 把几千张序列帧压制成带时间戳水印的 4K 延时视频。现在那台旧手机每天安静地对着窗外拍日出日落，我只需要坐在电脑前让 AI 修修脚本里偶尔冒出来的小问题，等着看每天自动合成好的延时预览。

## 尾声

这几个月高频使用 AI 写业余项目下来，我最大的感受是精力的分配方式变了。以前写个小工具，经常要为了查某个冷门 API 的参数或者调一段构建配置耗掉大半个晚上；现在这些琐碎的实现细节全部交出去之后，我反而有更多时间去琢磨贪吃蛇怎么走哈密顿路径、远控画面的卡顿到底卡在哪一层，以及整个系统的数据流该怎么切分才合理。当然，AI 生成的代码依然会频繁出错，有时候修好一个表面问题又在暗处引入两个新问题，所以人盯在前面看真机现象、读关键日志并随时把控方向依然是省不掉的。
